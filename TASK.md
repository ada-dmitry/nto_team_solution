# НТО. Мобильная разработка. Второй тур

## Командное задание backend — «Заявки на пропуск» (35 баллов)

Организация использует электронные пропуска. Сотрудник подаёт заявку на посещение организации гостем. Охрана рассматривает заявку через служебный API. Сотрудник видит решение в мобильном приложении, обновив список или детали заявки.

Backend-разработчик команды реализует **API заявок для сотрудников и служебный API охраны**.

---

## 1. Общие условия

### 1.1. Командный балл

Клиент и сервер командного задания проверяются **независимо**:

- backend проверяется отдельными API-тестами организаторов, без Android-приложения;
- Android-приложение проверяется с эталонным сервером организаторов, а не с вашим;
- решение напарника не используется при начислении баллов участнику;
- команда получает **максимальный балл за командную часть среди своих участников**, а не сумму.

`командный балл = max(баллы участников за командную часть)`

Пример: Android-разработчик получил 28, backend-разработчик — 22. Командный балл — 28 из 35.

### 1.2. Технологии

| Область | Значение |
|---|---|
| Язык и фреймворк | Kotlin 2.2.21, Spring Boot 3.5.7 |
| Данные | Spring Data JPA, Liquibase, PostgreSQL 17.10 |
| Сборка | Gradle 9.7.1 (wrapper входит в заготовку), JDK 17 |
| Формат обмена | JSON, UTF-8 |

Версии Spring, Jackson, JPA и Liquibase зафиксированы BOM Spring Boot. **Зависимости менять нельзя.**

### 1.3. Время и даты

- Все даты API имеют формат `yyyy-MM-dd'T'HH:mm:ss` без смещения: `2026-10-14T10:00:00`.
- Все значения трактуются во временной зоне `Europe/Moscow`, независимо от настроек сервера.
- Текущее время берётся **только** из внедрённого бина `Clock`. Системное время (`LocalDateTime.now()` без `Clock`, `System.currentTimeMillis()` и т. п.) в логике не используется: в тестах часы управляются организаторами.
- Серверные отметки времени сохраняются с точностью до секунды.

Примеры дат в задании иллюстративные. Тесты задают своё время и свои данные.

## 2. Предметная область

### 2.1. Пользовательский сценарий

1. Сотрудник входит в мобильное приложение по выданному четырёхсимвольному коду.
2. Просматривает только свои заявки.
3. Создаёт заявку на посещение гостем организации.
4. Охрана через служебный API одобряет или отклоняет заявку.
5. Сотрудник обновляет список или детали и видит новый статус.
6. Пока заявка не рассмотрена, автор может её отменить.

**Не требуются:** интерфейс охраны, регистрация сотрудников, WebSocket и push-уведомления, создание `visitor` или `pass` при одобрении заявки, развёртывание сервера в интернете.

### 2.2. Статусы и переходы

| Текущий статус | Действие | Кто выполняет | Новый статус |
|---|---|---|---|
| `PENDING` | Одобрение | Охрана | `APPROVED` |
| `PENDING` | Отклонение с комментарием | Охрана | `REJECTED` |
| `PENDING` | Отмена | Автор | `CANCELLED` |

Остальные переходы запрещены. Повторное одобрение, отклонение или отмена возвращает `409`, даже если запрошен уже установленный статус.

### 2.3. Данные

Схема создаётся миграциями Liquibase заготовки.

Таблица `staff`:

| Поле | Назначение |
|---|---|
| `id` | Автоматически генерируемый ID |
| `code` | Уникальный четырёхсимвольный код входа |
| `full_name` | ФИО сотрудника, возвращается в профиле как `name` |

Таблица `pass_request`:

| Поле | Назначение |
|---|---|
| `id` | Автоматически генерируемый ID (`Long`) |
| `host_id` | Автор заявки, ссылка на `staff` |
| `full_name` | ФИО гостя |
| `phone` | Телефон гостя |
| `organization` | Организация гостя, необязательная |
| `purpose` | Цель посещения |
| `valid_from`, `valid_to` | Планируемый интервал посещения |
| `status` | Статус заявки |
| `comment` | Комментарий охраны, необязательный |
| `created_at`, `updated_at` | Время создания и последнего изменения |

Заявка хранит введённые данные гостя.

Учебные данные: четыре сотрудника с кодами `1111`, `2222`, `3333`, `4444` и заявки 1–4 разных авторов во всех статусах. Тесты заменяют начальные данные. **Привязывать логику к конкретным ID или кодам нельзя.**

## 4. Контракт API

Все методы, кроме служебного, используют код сотрудника в пути.

| Метод | Назначение | Успех |
|---|---|---|
| `GET /api/{code}/auth` | Проверить код | `200`, профиль |
| `GET /api/{code}/requests` | Получить свои заявки | `200`, массив |
| `GET /api/{code}/requests?status=PENDING` | Отфильтровать свои заявки | `200`, массив |
| `GET /api/{code}/requests/{id}` | Детали своей заявки | `200`, объект деталей |
| `POST /api/{code}/requests` | Создать заявку | `201`, объект деталей |
| `POST /api/{code}/requests/{id}/cancel` | Отменить свою заявку (тело не требуется) | `200`, объект деталей |
| `PATCH /api/admin/requests/{id}` | Решение охраны (заголовок `X-Admin-Key`) | `200`, объект деталей |

### 4.1. Вход и разграничение доступа

- Код содержит ровно четыре символа: латинские буквы `A–Z`, `a–z` и цифры `0–9`. Регистр значим. Пробелы не удаляются.
- Неверный формат кода — `400 {"error":"Invalid code format"}`.
- Правильный формат, но неизвестный код — `401 {"error":"Unauthorized"}` на всех пользовательских методах.
- Чужая заявка при чтении и отмене неотличима от отсутствующей: `404 {"error":"Request not found"}`.
- Служебный метод требует правильный `X-Admin-Key` (проверка уже готова, иначе `403 {"error":"Forbidden"}`). Отсутствующая заявка у охраны — тот же `404`.

Профиль:

```json
{"name":"Иванов Иван Иванович"}
```

### 4.2. Список

```json
[
  {
    "id": 12,
    "fullName": "Сидоров Пётр Ильич",
    "validFrom": "2026-10-14T10:00:00",
    "validTo": "2026-10-14T16:00:00",
    "status": "PENDING"
  }
]
```

- Только заявки текущего сотрудника.
- Сортировка по `validFrom` по возрастанию, затем по `id` по возрастанию. Пустой результат — `[]`. Пагинация не требуется.
- Параметр `status` необязателен; без него возвращаются все статусы. Допустимы только `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED`. Пустое значение, неизвестное значение, пробелы или другой регистр — `400 {"error":"Invalid status"}`.

### 4.3. Объект деталей

Используется в ответах деталей, создания, отмены и решения охраны:

```json
{
  "id": 12,
  "fullName": "Сидоров Пётр Ильич",
  "phone": "+79991234567",
  "organization": "ООО НТО",
  "purpose": "Встреча с сотрудником",
  "validFrom": "2026-10-14T10:00:00",
  "validTo": "2026-10-14T16:00:00",
  "status": "REJECTED",
  "comment": "Сотрудник отсутствует в указанный день",
  "createdAt": "2026-10-10T12:31:05",
  "updatedAt": "2026-10-10T15:02:44"
}
```

`organization` и `comment` при отсутствии значения присутствуют в ответе как `null`.

### 4.4. Создание

Тело запроса:

```json
{
  "fullName": "Сидоров Пётр Ильич",
  "phone": "+79991234567",
  "organization": "ООО НТО",
  "purpose": "Встреча с сотрудником",
  "validFrom": "2026-10-14T10:00:00",
  "validTo": "2026-10-14T16:00:00"
}
```

- Клиент не передаёт автора, статус, комментарий и служебные даты; лишние поля игнорируются.
- Автор определяется по коду, статус — `PENDING`, комментарий — `null`, `createdAt` и `updatedAt` равны текущему времени из `Clock`.
- Ответ — `201` с полным объектом деталей.

### 4.5. Решение охраны

- Одобрение: `{"status":"APPROVED"}`. Переданный при одобрении `comment` игнорируется; у одобренной заявки `comment` равен `null`.
- Отклонение: `{"status":"REJECTED","comment":"Сотрудник отсутствует в указанный день"}`. Комментарий обязателен.
- Служебный метод принимает только целевые статусы `APPROVED` и `REJECTED`; `CANCELLED` устанавливается только методом отмены.

### 4.6. Отмена

Отмена разрешена только автору и только из `PENDING`. Тело запроса не требуется.

### 4.7. Отметки времени

После успешного решения или отмены `updatedAt` берётся из `Clock`, `createdAt` не меняется. Если часы не сдвинулись, новое значение `updatedAt` может совпасть с предыдущим.

## 5. Валидация

Тела запросов приходят как `CreateRequestBody` и `DecisionBody`, где **все поля — строки** (`String?`). Разбор дат и статусов и проверку обязательных полей выполняете вы, поэтому ошибки этих полей возвращаются в формате `errors`, а не как `Invalid request body`.

Перед проверкой длины у всех строковых полей удаляются начальные и конечные пробелы. Сохраняются нормализованные значения.

| Поле | Правило |
|---|---|
| `fullName` | Обязательно; 5–150 символов после нормализации |
| `phone` | Обязательно; `+7` и ровно 10 ASCII-цифр `0–9`; удаляются только крайние пробелы, пробелы и разделители внутри номера недопустимы |
| `organization` | Необязательно; до 150 символов; отсутствие, `null`, пустая строка и строка из пробелов сохраняются как `null` |
| `purpose` | Обязательно; 5–200 символов после нормализации |
| `validFrom` | Обязательно; строго формат `yyyy-MM-dd'T'HH:mm:ss` и существующие дата и время; не раньше точного текущего момента из `Clock`, с учётом долей секунды: при часах `09:00:00.789` начало `09:00:00` недопустимо, `09:00:01` допустимо; если часы стоят на целой секунде, ровно это время допустимо |
| `validTo` | Обязательно; строго тот же формат; позже `validFrom` и в тот же календарный день (`00:00` следующих суток — уже другой день) |
| `status` в решении охраны | Обязательно; `APPROVED` или `REJECTED` после нормализации |
| `comment` при отклонении | Обязательно; 1–500 символов после нормализации (строка из пробелов — ошибка) |

Длина считается в символах; тесты используют обычные буквы и цифры. Дата без секунд, с пробелом вместо `T` или несуществующая (`2026-02-30T10:00:00`) — ошибка поля.

Ответ на ошибки полей — `400`:

```json
{
  "errors": {
    "phone": "Укажите телефон в формате +7XXXXXXXXXX",
    "validTo": "Окончание должно быть позже начала в тот же день"
  }
}
```

- Возвращаются **все** обнаруженные ошибочные поля сразу.
- Пропущенное или `null` обязательное поле — ошибка соответствующего поля.
- Если дата не разбирается, возвращается ошибка её поля; сравнение дат выполняется только для успешно разобранных значений.
- Ключи `errors` фиксированы и совпадают с именами полей тела: `fullName`, `phone`, `organization`, `purpose`, `validFrom`, `validTo`, `status`, `comment`. Ошибка формата или прошедшего времени начала — `validFrom`; ошибка формата окончания и «не позже начала / не в тот же день» — `validTo`.
- Точный текст сообщений не оценивается, но сообщения должны быть непустыми.
- `400 {"error":"Invalid request body"}` готовый обработчик возвращает только для синтаксически некорректного JSON или значения нестрокового типа, например числа вместо строки.

## 6. Дубликаты, переходы и порядок проверок

### 6.1. Дубликаты

Дубликат — заявка **того же автора**, с тем же нормализованным телефоном, в статусе `PENDING` или `APPROVED`, интервал которой пересекается с новым.

Интервалы полуоткрытые: пересечение есть, если `newFrom < existingTo` и `existingFrom < newTo`. Интервалы, соприкасающиеся одной границей (10:00–11:00 и 11:00–12:00), не пересекаются. Заявки других авторов, с другим телефоном, отклонённые и отменённые заявки не препятствуют созданию.

Дубликат — `409 {"error":"Duplicate request"}`.

### 6.2. Ошибки переходов

| Ситуация | Ответ |
|---|---|
| Заявка отсутствует или недоступна автору | `404 {"error":"Request not found"}` |
| Исходный статус уже не `PENDING` | `409 {"error":"Invalid status transition"}` |
| Неизвестный или недопустимый для метода целевой статус | `400 {"errors":{"status":"..."}}` |
| Нет допустимого комментария для отклонения | `400 {"errors":{"comment":"..."}}` |

### 6.3. Порядок проверок

- Чтение, отмена, решение охраны: доступ вызывающего (код или ключ) → наличие и принадлежность заявки → корректность тела → допустимость перехода.
- Создание: доступ → валидация → дубликат.
- Неизвестный код и неверный параметр `status` одновременно — `401` (доступ проверяется раньше).

### 6.4. Транзакции и хранение

- Создание и смена статуса выполняются транзакционно, изменения **реально фиксируются** в PostgreSQL.
- При любой ошибке данные в БД не меняются.
- **Ничего не кешируйте в памяти** между запросами: тесты меняют данные напрямую в БД, и каждый запрос должен читать актуальное состояние.
- Тесты выполняют изменения последовательно; нагрузочные и конкурентные сценарии не оцениваются. Конфликт «заявку уже рассмотрели до отмены» проверяется последовательностью запросов и должен приводить к `409`.

## 8. Примеры проверочных сценариев

Примеры поясняют перечисленные требования и не вводят дополнительных баллов.

**Доступ к чужой заявке.** У сотрудника `2222` есть заявка → запрос её деталей с кодом `1111` — `404` → попытка отменить её с кодом `1111` — `404` → заявка в БД не изменилась.

**Граница пересечения.** У автора есть ожидающая заявка для телефона `+79991234567` с 10:00 до 11:00 → новая заявка того же автора для этого телефона с 10:30 до 12:00 — `409` → новая заявка с 11:00 до 12:00 — `201` (интервалы только соприкасаются).

**Решение принято перед отменой.** Охрана одобряет ожидающую заявку → автор пытается её отменить — `409 Invalid status transition`, данные не меняются.

**Отклонение.** Охрана отклоняет заявку с комментарием `  Нет пропуска  ` → в ответе и в БД статус `REJECTED`, комментарий `Нет пропуска`, `updatedAt` равен текущему времени `Clock`, `createdAt` прежний. Повторное отклонение — `409`.

## 9. Как проходит проверка

- После отправки ссылки проверяющая система сама поднимает изолированную PostgreSQL, применяет миграции, запускает ваш сервер и API-тесты. Разворачивать сервер в интернете не нужно.
- Защищённые файлы (раздел 3.1) восстанавливаются из заготовки.
- Перед каждым сценарием тесты восстанавливают исходные данные и часы. Записи для проверки списка, деталей, отмены и решения охраны создаются через JDBC, а не только вашим `POST`, поэтому ошибка в создании заявки не обнуляет баллы за остальные методы. Последовательности ID согласованы с данными — создание заявки не приводит к конфликту ID.
- Модель проверяется через JPA-метаданные и реальную запись в БД, а не по именам ваших классов.
- Сервер должен **запускаться**, а решение — **компилироваться**. Иначе баллы не начисляются.
- Скрытые тесты проверяют перечисленные требования на других данных, но не вводят новых требований.

### Локальный запуск

Нужны Docker с плагином Docker Compose и клиентские утилиты PostgreSQL 17 (`psql`, `createdb`, `pg_isready`). Команды выполняются из корня заготовки.

```bash
docker compose -p nto_team_local -f compose.yml up -d --wait
export DB_URL=jdbc:postgresql://127.0.0.1:5435/nto_team DB_USER=nto DB_PASSWORD=nto
export ADMIN_KEY=teaching-admin
./gradlew bootRun
```

- БД доступна на `localhost:5435`. Если порт занят, меняйте `compose.yml` и переменные окружения, а не `application.yml`.
- `SERVER_PORT` задаёт порт HTTP (по умолчанию 8080).
- Liquibase создаёт таблицы и учебные данные один раз; перезапуск их не сбрасывает.
- Учебный ключ `teaching-admin` не является секретом — не публикуйте этот сервер в интернете.

Проверка вручную:

```bash
curl http://localhost:8080/api/1111/auth
curl http://localhost:8080/api/1111/requests
curl -X PATCH http://localhost:8080/api/admin/requests/1 \
  -H 'X-Admin-Key: teaching-admin' -H 'Content-Type: application/json' \
  -d '{"status":"APPROVED"}'
```

### Тесты

**Тесты сбрасывают данные.** Используйте отдельную одноразовую БД, а не учебную с ручными данными. Запускайте проверки последовательно.

```bash
PGPASSWORD=nto createdb -h 127.0.0.1 -p 5435 -U nto nto_team_test
DB_URL=jdbc:postgresql://127.0.0.1:5435/nto_team_test DB_USER=nto DB_PASSWORD=nto \
  ./gradlew test --rerun-tasks --no-build-cache
```

В заготовке нет тестов. Собственные тесты можно добавлять в `src/test/kotlin/ru/nto/team/` (зависимость `spring-boot-starter-test` подключена), но при оценке они не используются: проверку выполняют закрытые тесты организаторов.

Остановка БД без потери данных: `docker compose -p nto_team_local -f compose.yml down`. Не добавляйте `-v` — это удалит учебный том.

## 10. Сдача

1. Создайте **публичный** репозиторий на GitHub и положите проект **в его корень** — так, как он лежит в заготовке (`settings.gradle.kts` в корне).
2. Отправьте ссылку на репозиторий в соответствующее задание Moodle. Pull Request создавать не нужно.
3. Проверяется последний коммит ветки по умолчанию на момент отправки ссылки. Изменения, отправленные позже, без повторной отправки ссылки не проверяются.

Порядок повторной сдачи и сроки определяет регламент организаторов. Результат и баллы по критериям публикуются в Moodle. Команда получает **максимум** из баллов участников за командную часть.
