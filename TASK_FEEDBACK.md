# Подтверждённые замечания к заготовке

## 1. Отсутствующий Gradle Wrapper JAR

В использованной участнической заготовке были `gradlew`, `gradlew.bat` и
`gradle/wrapper/gradle-wrapper.properties`, но отсутствовал
`gradle/wrapper/gradle-wrapper.jar`. Поэтому одного установленного JDK 17
недостаточно для запуска включённого wrapper.

В решении JAR восстановлен из официального тега Gradle `v9.7.1`:

- источник: <https://raw.githubusercontent.com/gradle/gradle/v9.7.1/gradle/wrapper/gradle-wrapper.jar>;
- контрольная сумма: <https://services.gradle.org/distributions/gradle-9.7.1-wrapper.jar.sha256>;
- совпавший SHA-256: `7a9ce74cff467ca1bf60a4fcd9f05185acceda4d0f382434d393e17864262c5d`.

Версия wrapper, настройки сборки и зависимости не изменены.

## 2. Порядок проверки доступа и разбора JSON

ТЗ §6.3 задаёт порядок «доступ → наличие/принадлежность → тело → переход».
Обычный вызов сервиса из готового контроллера с `@RequestBody` не обеспечивает
этот порядок для синтаксически некорректного JSON: Spring разбирает тело до
вызова метода контроллера.

Подтверждённый пример до добавления ранней проверки:
`POST /api/ZZ99/requests` с телом `{` возвращал `400 {"error":"Invalid request body"}`,
хотя код неизвестен и по ТЗ должен иметь приоритет `401 {"error":"Unauthorized"}`.
Аналогично проверка отсутствующего ID охраны отставала от ошибки JSON.

По согласованию реализован строгий порядок из ТЗ: дополнительный
`RequestAccessAdvice` выполняет проверки до преобразования тела, в том числе
пустого. Защищённые контроллерные DTO, `MalformedBodyAdvice`, проверка ключа
и конфигурация не изменены. Поведение проверяется `ContractIntegrationTest`.
Для доступного сотрудника или существующей заявки некорректный JSON по-прежнему
возвращает предусмотренный готовой инфраструктурой `400 Invalid request body`.
